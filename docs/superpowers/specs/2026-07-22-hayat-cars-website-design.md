# Сайт-вітрина автосалону Hayat Gruppe

Дата: 2026-07-22
Статус: узгоджено, готово до планування

## Навіщо це

Автодилер у Відні (Hayat Gruppe) продає б/в авто. Сайт робиться йому в подарунок —
власник проєкту хоче принести готовий результат, тому дилер про роботу не знає
і його ні про що не питають. З цього випливає жорстке обмеження: **усі дані
беруться з публічних джерел, доступу до його акаунтів немає**.

Сайт має дві роботи одночасно:
1. Дилер кидає клієнту в месенджер посилання на **конкретне авто**.
2. Дилер кидає посилання на **сайт загалом** як візитівку.

Обидві однаково важливі, тому і головна, і сторінка авто мають бути сильними.

Каталог наповнюється сам із willhaben — дилер нічого не адмініструє. Це головна
проєктна вимога: **сайт має жити роками без ручної роботи**.

## Межі

**Входить:** авто, каталог, синхронізація, три мови, контактні CTA, юридичні сторінки.

**Не входить:** нерухомість, фінансування, система AKITA, інвестиції. Це решта
бізнесу Hayat Gruppe, вона лишається на існуючому hayatgruppe.com (Wix),
який ми не чіпаємо. Нерухомість можлива другою хвилею, але архітектуру
під неї спеціально не готуємо (YAGNI).

**Не входить також:** адмінка, форма заявки, авторизація, збереження
персональних даних. Нічого з цього не потрібно, і кожне з них створює
обовʼязок обслуговування, якого в подарунку бути не повинно.

## Джерело даних

Повний розбір із перевіркою на живих даних —
[willhaben-source-analysis.md](../../research/willhaben-source-analysis.md).

Стисло:

```
https://www.willhaben.at/iad/haendler/hayatgruppe/auto/?orgId=1004471&page=1&rows=200
```

Весь сток (99 авто) повертається **одним запитом за ~0.6 с**. Дані лежать
у `__NEXT_DATA__` як JSON — верстку не парсимо, 57 структурованих полів на авто.

Джерело ховається за інтерфейсом `InventorySource`, щоб скрейпер можна було
замінити на офіційний дилерський фід, не переписуючи решту системи.

## Архітектура

Обрано варіант «статика + тонкий живий шар». Причина — ліміти безкоштовних
тарифів Cloudflare (перевірені за документацією):

| Ресурс | Ліміт | Наше споживання |
|---|---|---|
| Pages, білди | 500/міс | лише на реальну зміну, ~2–10/добу |
| Workers, запити | 100 000/добу | 96 запусків cron |
| Workers, cron | 5 тригерів | 1 |
| KV, записи | 1 000/добу | не використовуємо KV |
| R2, сховище | 10 ГБ | ~185 МБ фото |
| R2, egress | безкоштовно | весь трафік фото |

Перебудовувати сайт на кожен синк не можна — 2 880 білдів на місяць
проти ліміту 500. Тому свіжість відвʼязана від білдів.

### Чотири компоненти

**1. Sync Worker** — Cloudflare Worker, cron `*/15 * * * *`.
Тягне сторінку → дістає JSON → нормалізує → рахує хеш змісту → вирішує,
що робити далі.

**2. Дзеркало фото** — частина Sync Worker. Фото нових авто копіюються
в R2 під `cars/{adId}/{n}.webp`. Фото проданих зберігаються **ще 7 днів**,
щоб уже розіслані посилання не ламались одразу.

**3. Білд сайту** — Astro читає `catalog.json` з R2 і генерує статику:
головна, каталог, сторінка кожного авто, OG-картинки, ×3 мови.
Запускається через Pages Deploy Hook **лише коли хеш змісту змінився**.

Білд забирає `catalog.json` **звичайним HTTP-запитом на публічний домен
бакета R2**, без ключів доступу. Це навмисно: інакше довелося б класти
S3-креденшели в налаштування збірки Pages, а це секрет, який нічого не захищає —
дані й так публічні. Фото так само віддаються з R2 напряму, повз Workers,
тому трафік сайту не витрачає квоту запитів.

**4. Живий шар** — `live.json` у R2 (~5 КБ), оновлюється щоцикл незалежно
від білдів. Сторінка тягне його при відкритті й коригує ціни та позначає продані.

```
willhaben ──15 хв──> Sync Worker ──> перевірка осудності
                          │                    │
                          │              не пройшла → лишити попередній стан
                          │                            + записати помилку в status.json
                          │                    │
                          │              пройшла → live.json (завжди)
                          │                         │
                          │                    хеш змінився?
                          │                         │
                          │                    так → фото в R2
                          │                          catalog.json
                          │                          Pages Deploy Hook
                          │
                          └── R2 ──> браузер клієнта (egress безкоштовний)
```

## Модель даних

Канонічний `Car` — єдина форма, якою користується решта системи:

```
id            ADID, стабільний ідентифікатор willhaben
uuid          AD_UUID
slug          "bentley-azure-1619051774" (модель + id, стабільний)
make          "Bentley"
model         "Azure"          — після чистки від спаму
title         "Bentley Azure"  — очищений HEADING
price         330000           — число, для сортування й фільтрів
mileage       6800
year          2023
fuel          код + локалізовані назви
transmission  код + локалізовані назви
powerKw       кВт (в UI показуємо і к.с.)
bodyType      код + локалізовані назви
seats, owners, colour
condition, warranty
equipment[]   коди + локалізовані назви
images[]      { r2Key, order }
location      { city, postcode, district, lat, lng }
willhabenUrl  посилання на оригінал
publishedAt, updatedAt
contentHash   хеш значущих полів
```

**`contentHash` рахується лише зі значущих полів** — ціна, пробіг, заголовок,
склад фото, наявність. `LAST_UPDATED` і `IS_BUMPED` у хеш **не входять**:
дилери постійно «піднімають» оголошення, це змінює час, але не зміст.
Якби ми враховували їх, сайт перебудовувався б щогодини даремно і зʼїв би ліміт білдів.

`live.json`:

```json
{ "generatedAt": "...", "cars": { "1619051774": { "price": 330000, "available": true } } }
```

| Головна | `/de/` | Візитівка. Хто він + найсильніше зі стоку |
| Каталог | `/de/fahrzeuge/` | Усі авто, фільтри повністю клієнтські |

Фільтри каталогу (марка, ціна, рік, паливо, коробка, кузов) працюють **у браузері

### OG-картинки

Кожному авто генерується власна OG-картинка на етапі білду: фото, модель, ціна, лого.
Це прямо обслуговує головний сценарій — коли дилер кидає лінк у WhatsApp,
той розкривається карткою, що продає, а не сірим прямокутником.

## Візуальний напрямок: Nocturne

Темна редакційна подача. Майже чорне тло, тепло-біла типографіка, один акцентний колір.
Фото живуть у рамах з великими полями, як у каталозі аукціонного дому.
Скрол повільний і важкий, авто відкриваються як експонати.
Анімації — GSAP + ScrollTrigger, плавний скрол — Lenis.

**Обмеження диктує стиль.** Фото 1178×785 не витримають повноекранного hero —
на великому моніторі вони митимуть. Але в редакційному обрамленні з повітрям
вони виглядають бездоганно. Тому: **жодного full-bleed фото на весь екран**.
Темне тло додатково маскує стелю роздільної здатності — око читає глибину, а не пікселі.

### Ієрархія стоку

Сток «штангою»: від €299 до €330 000, медіана €17 999. Ділити на розділи
«преміум» і «решта» не можна — сток оновлюється сам, преміум-розділ спорожніє
після продажу, і полагодити це нікому. **Будь-яка ручна курація тут помре.**

Тому ієрархія обчислюється з даних на момент білду:

- **Топ стоку** — **3 найдорожчі авто** на момент білду: велика редакційна
  подача на головній.
- **Верхній сегмент** — ціна **вище подвоєної медіани** стоку: крупніші картки в сітці.
- **Решта** — рівна чиста сітка.

Пороги рахуються від наявного стоку, не задаються константами в коді.
Якщо медіана зміститься, ієрархія перебудується сама.

Правило, яке не порушується: **дешеве авто ніде не виглядає дешевим**.
Менше площі — так. Гірша типографіка, ярлики «бюджетне», сірі картки — ні.
Покупець Skoda не має відчути, що потрапив не туди.

## Відмови й стійкість

**Головне правило: помилка ніколи не спорожнює сайт.**

Це найбільший ризик конструкції. Наївний код, отримавши збій, запише «нуль авто»,
запустить білд, і клієнт відкриє порожню вітрину — а дізнається про це власник
від дилера, а не з логів.

Перед публікацією стан проходить перевірку осудності. **Не пройшов — попередній
стан лишається недоторканим:**

| Умова | Дія |
|---|---|
| HTTP не 200 | Лишити попередній стан |
| `__NEXT_DATA__` не знайдено чи не парситься | Лишити попередній стан |
| Розпізнано 0 авто | Лишити попередній стан |
| Кількість авто впала більш ніж удвічі за цикл | Вважати збоєм, лишити попередній стан |
| Обовʼязкові поля відсутні в >20% оголошень | Лишити попередній стан |

Останній справний знімок завжди лежить у R2 — відкотитись є куди завжди.

**Здоровʼя системи:** Worker щоцикл пише `status.json` у R2 — час останнього
успішного синку, кількість авто, остання помилка. Це джерело правди про стан.
Додатково передбачено необовʼязковий `ALERT_WEBHOOK_URL` у змінних оточення:
якщо заданий, при переході в стан помилки туди йде повідомлення (Telegram/Discord).
За замовчуванням не налаштований — система працює без нього.

**Ввічливість до джерела:** один запит на цикл, чесний User-Agent,
експоненційна пауза при 429/5xx. Обхід захисту (ротація проксі, розвʼязування капч)
не реалізується — якщо willhaben почне блокувати, це сигнал переходити
на офіційний фід, а не ескалювати.

## Тестування

**Парсер і нормалізація** — основне покриття. Фікстури реальних даних уже
збережені в [`docs/research/fixtures/`](../../research/fixtures/): три оголошення
з різних кінців цінового діапазону та знімок стоку на 99 позицій.
Тести золотих файлів: фікстура → очікуваний `Car`.

Окремо перевіряються: чистка заголовків від спаму, відновлення моделі
з `MODEL_SPECIFICATION`, повнота словника перекладів (жодного нерозпізнаного коду).

**Перевірка осудності** — таблиця вище перетворюється на таблицю тестів,
по одному на рядок. Це найважливіші тести в проєкті.

**Обчислення хеша** — «підняте» оголошення (змінився лише `LAST_UPDATED`)
**не має** давати новий хеш. Змінена ціна — має.

**Верстка** — сторінка авто перевіряється на трьох мовах на найдовших рядках.

## Що потрібно вирішити перед запуском

Це не блокує розробку, але блокує публікацію:

1. **Домен** — не обрано. Потрібен окремий від hayatgruppe.com, ~€12/рік.
2. **WhatsApp** — не підтверджено, що `+43 676 5571571` підключений до WhatsApp.
   Перевіряється відкриттям `wa.me/436765571571`. Якщо номер не в WhatsApp —
   кнопка прибирається, лишаються дзвінок і пошта.
3. **Юридичні тексти** — скопіювати Impressum, Datenschutz, AGB з чинного сайту.
4. **Лого** — доступне з willhaben-даних (`AD_SEARCHRESULT_LOGO`), але
   в низькій якості. Для OG-картинок і шапки бажано знайти кращий варіант.

## Свідомо не робимо

- Адмінку й будь-яку авторизацію — сайт наповнюється сам.
- Форму заявки — створює обовʼязок обслуговування.
- Кешування чи БД поза R2 — 99 записів не потребують бази.
- Підтримку нерухомості — поза межами задачі.
- Обхід антибот-захисту — межа проведена свідомо.
