# hayat-sync

Cloudflare Worker: раз на 15 хвилин переносить сток дилера з willhaben у R2.

## Що публікує

| Ключ | Призначення | Частота |
|---|---|---|
| `catalog.json` | Повний каталог для збірки сайту | лише при зміні змісту |
| `live.json` | Ціни й доступність (~5 КБ) | щоцикл |
| `status.json` | Стан синхронізації | щоцикл |

## Головне правило

Збій ніколи не публікує порожній каталог. Перед записом стан проходить
перевірку осудності (`src/sanity.ts`); не пройшов — попередній стан
лишається недоторканим.

## Команди

    npm test              тести
    npm run typecheck     перевірка типів
    npx wrangler deploy   розгортання
    curl .../status       поточний стан

## Секрети

    wrangler secret put PAGES_DEPLOY_HOOK    запуск перебудови сайту
    wrangler secret put ALERT_WEBHOOK_URL    необовʼязково: сповіщення про збої

## Перший деплой: сідинг фото

Worker дзеркалить фото порційно — щонайбільше `IMAGES_PER_CYCLE` (40) fetch-спроб
за один виклик, бо безкоштовний тариф Cloudflare дозволяє лише 50 зовнішніх
запитів на виклик. Проти порожнього бакета це означає, що весь сток (~99 авто,
~3400 фото) дозавантажиться лише за ~85 циклів (~21 годину), а `catalog.json`
не публікується, поки перевірка осудності (`checkSanity`) не побачить достатньо
живих фото.

Щоб сайт з'явився одразу, ОДИН РАЗ, локально, на Node ≥22, з R2-кредами в
середовищі, ПЕРЕД першим `wrangler deploy` — запустіть скрипт сідингу. Він
працює поза Worker'ом, тож ліміт subrequest'ів на нього не діє, і заливає
все дерево фото напряму через S3-сумісний API R2.

    WILLHABEN_ORG_ID=... \
    USER_AGENT=... \
    R2_ACCOUNT_ID=... \
    R2_ACCESS_KEY_ID=... \
    R2_SECRET_ACCESS_KEY=... \
    R2_BUCKET=... \
    npm run seed

`--dry-run` (`npm run seed -- --dry-run`) лише показує план — кількість фото
й перші кілька ключів — і нічого не заливає.

Після сідингу Worker підтримує лише дельти: нові авто й нові фото на кожному
циклі, без повторного заливання вже наявного.
